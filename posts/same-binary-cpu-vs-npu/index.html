Same binary, CPU vs NPU

What changes when one 4-billion-parameter model moves from a board's CPU cores to its neural accelerator, with everything else held fixed: same model file, same runtime binary, same prompts, same harness. One flag differs.

Most CPU-versus-NPU comparisons change three things at once: the model format, the runtime, and the compute unit, then report one number and call it a hardware comparison. This post changes one thing. It is the measurement behind two claims made elsewhere on this blog: that the compute unit changes speed only, which closed a gap in the serving-path finding, and that agent workloads live in prefill while chat lives in decode. Every number is from one afternoon on a Qualcomm QCS9075, five repetitions per row, run-to-run spread under one percent. Measured 10 September 2026.

Summary

The NPU reads the prompt five to seven times faster and writes the answer about 40% slower. Accuracy on a 65-case agent benchmark was identical on both paths, 98.5%. Because an agent turn is mostly prompt, a turn took 52.5 s on the CPU and 14.5 s on the NPU. The compute unit changes speed only, and where it changes it is prefill.

What an agent feels

An agent turn is a long prompt and a short answer: system instructions, tool schemas and device output add up to about 2.7K tokens in, with a structured tool call of about 50 tokens out. That shape is nearly all prefill, so the prefill column decides the turn.

The compiled path, kept separate

The board vendor's serving stack can also run this model as a fixed NPU graph compiled ahead of time (a W4A16 bundle) rather than through llama.cpp. Measured the same way: 716 to 1,094 tok/s prefill, first token 0.36 s at 256 tokens and 2.0 s at 2,044, decode 16.1 to 13.1 tok/s over long generations.

It is a different model format, so it is not part of the controlled pair, and it scored 92.3% on the same benchmark against 98.5% for the GGUF paths. The fastest path is not the most accurate one; the six-point gap is the format, not the silicon. (The 2,795-token row could not be measured on this path in the serving version used, a generation-length limitation fixed in a newer release.)

Why the CPU wins decode

  • Prefill processes the whole prompt in parallel: compute-bound, exactly what a matrix accelerator is built for.
  • Decode produces one token at a time and is bound by memory bandwidth; on this board the NPU shares that memory with the CPU, so it gains nothing there, and each token also pays a round trip between CPU and accelerator. At this model size that tax exceeds the accelerator's gain.
  • Public leaderboards rank decode, the one phase where a CPU holds its own. For chat that is the right column. For agents, retrieval and summarization, rank by prefill and first token instead.

The mechanism behind these numbers, without the numbers, is written up separately as "Chat is decode, agents are prefill". The accuracy side of the same afternoon, the 98.5% that did not move between compute units and the six points the compiled format costs, is in the serving-path post.
