FastRPC: the 1.5 GB wall between the CPU and the Qualcomm NPU

Stubs, skels, and DMA heaps: the plumbing every Hexagon NPU workload lives on, and the three classes of failure it produces.

Every byte that reaches the Hexagon NPU crosses a boundary called FastRPC, and three whole classes of production failure are consequences of how that boundary works: a silent fallback to the CPU, a hard memory ceiling that turns context length into a load-time coin flip, and cleanup mistakes that leave the board needing a reboot. This post makes the boundary visible: its parts by name, each failure with its fingerprint, the KV-cache arithmetic that predicts the ceiling, and a bring-up checklist. It is the NPU deep dive behind the memory-hierarchy post. Board: Qualcomm QCS9075 on the Dragonwing IQ-9075 EVK, Hexagon v73, Qualcomm Linux, QAIRT 2.45. Every failure described was observed on it.

The bundle loaded perfectly. An 8-billion-parameter model, compiled for a 16K context, weights mapping into memory without complaint. Then the first request came in, and the runtime answered with:

fastrpc_mmap … Cannot allocate memory

Error 6001. Every subsequent request, the same. The model was there, its weights had mapped, but no inference could run, because there was no room left to map the thing inference actually needs. And when I did the obvious thing, killed the process and retried, the board did not recover cleanly: the kernel began retrying a registration that could never succeed, flooding the console, and the box needed a reboot to come back.

This is the least glamorous part of running a model on this silicon, and, I think, among the most useful. You cannot debug what you cannot see, and FastRPC is invisible until it breaks.

FastRPC anatomy: two processors, one phone line

The CPU and the Hexagon NPU share the board's DRAM but not an address space. To run a computation on the DSP, the CPU makes a remote procedure call across a bridge, FastRPC, and that call has a specific machinery you have to know by name to debug.

The stub, CPU side. Your process links libcdsprpc.so, the CPU-side stub. It is the client end of the phone line: it marshals arguments, hands buffers to the kernel FastRPC driver, and blocks waiting for the DSP to answer.

The skel, DSP side. The code that runs on the Hexagon is packaged as a skel, short for skeleton: a DSP-compiled library loaded onto the compute DSP at runtime. The runtime finds skels through an environment variable, and here is an important misnomer on the platform:

ADSP_LIBRARY_PATH=/opt/qairt/2.45.0.260326/lib/hexagon-v73/unsigned

The variable says ADSP, audio DSP, but it governs the cDSP, the compute DSP, the one running your model. The name is a historical artifact. If this variable is wrong, unset, or points at the wrong Hexagon version, the skel is not found, and that failure is silent. Note also the unsigned at the end of the path: that is the unsigned protection domain. The DSP can run code in a signed domain, vendor-signed, for secure workloads, or an unsigned one; open LLM work runs in the unsigned one, which is why the skels live there.

The shared buffers. The CPU and the DSP exchange tensors through DMA heaps, memory both can map:

/dev/dma_heap/system
/dev/dma_heap/qcom,cma-secure-cdsp

The device nodes. The bridge to each DSP domain is a device file, /dev/fastrpc-cdsp and /dev/fastrpc-cdsp1 for the two compute domains on this chip, and the kernel driver ferries calls across. That is the apparatus end to end: stub, kernel driver, DSP domain, skel, with tensors passed in DMA-heap buffers. Keep the picture; all three failure classes are failures of this picture.

Failure class 1: the silent CPU fallback

Here is an easy way to lose a week on this platform, and it produces no error at all.

If the library path is unset or wrong, the runtime cannot load the DSP skel. On the llama.cpp path especially, the sensible-seeming behavior kicks in: it falls back to the CPU, runs your model correctly, with the right output, and never tells you the NPU was never involved. You asked for the NPU on the command line, you got a coherent answer, you shipped it, and it ran on the CPU the whole time.

In my experience this is the first thing to suspect when "the NPU flag did nothing." The flag did do something: it asked for the NPU, the skel was not found, and the graceful fallback swallowed the failure. The lesson is the one every measurement on this blog rests on: never trust that offload happened; measure it. The same-binary post is what that measurement looks like, and when it says everything ran on the CPU, the first thing to check is whether the library path is set and points at the skels for your Hexagon version, v73 here, not v75.

Failure class 2: the wall

Now the failure from the cold open, and the arithmetic that predicts it.

Each inference context needs contiguous DSP-side memory mappings, and there is a hard ceiling on how much can be mapped. The DSP's DMA address space is about 1 GB per compute domain; in practice an inference context gets roughly 1 to 1.5 GB of mapped memory before allocations start to fail. Two things compete for it: the model's working set and the KV cache, the per-token attention memory that grows with context length. Weights can be handled with mapping strategies that ease the pressure, an 8B model that failed to map in five parts of up to 1.2 GB loaded fine in eight parts each under 1 GB. The KV buffer is a single allocation that scales linearly with context, and it has to fit.

So "how long a context can I run?" is not a software preference. It is a memory-budgeting problem against a fixed hardware ceiling, and you can do the sum in advance. For a 4B model with 8-bit KV and grouped-query attention, the cache costs about 72 KB per token; for an 8B model about 76 KB.

Compiled contextKV buffer, 4B modelUnder the ceiling?
4Kabout 344 MByes; proven stable, the deployed configuration
8Kabout 700 MByes; measured, at about twice the per-turn time
16K1.2 to 1.5 GBno; error 6001, reproduced with an 8B 16K bundle

The 16K row is the cold open. The weights mapped; then the KV allocation collided with the ceiling, fastrpc_mmap returned "Cannot allocate memory", and every request failed at the mapping step with error 6001. Not a slow context; a non-loading one. On this silicon a too-long context does not degrade gracefully. It fails to allocate, hard, at load or at the first request.

When FastRPC mapping is under pressure, the kernel log shows it. From this board's dmesg:

qcom,fastrpc-cb 26300000.remoteproc:glink-edge:fastrpc:compute-cb@2: failed to map buffer, fd = 120
qcom,fastrpc-cb ...:compute-cb@3: failed to map buffer, fd = 120

Those "failed to map buffer" lines on the FastRPC compute context banks are the fingerprint of the boundary refusing an allocation. When you see them, you are not looking at a model bug. You are looking at the wall.

A third, smaller form of the same wall: loading a bundle in many parts can fail on the fourth part not because memory ran out but because the kernel's default limit on memory mappings per process was too low for that many large maps. Raising vm.max_map_count fixed it, and the setting is lost on a reflash, so it belongs in the board image.

The consequence: context length is a compile-time decision

This is why the compiled bundle's context length is baked in and cannot be raised with a runtime flag. The context window is not a configuration knob you turn; it is a hardware budget you commit to when you compile, and getting it wrong means the artifact does not load at all. The context-window post is the other half of the trade: the 8K build fits, and runs about 1.9 times slower per turn, because a fixed-shape graph pays for the whole window on every token. Choose the window deliberately: enough for the workload, comfortably under the KV ceiling, and no more.

It also dictates a server-layer rule: reject oversize prompts before they reach the engine. If the context is 4096 and a 6000-token request arrives, the right behavior is an immediate, clean HTTP error, not handing it to the runtime and discovering the wall the hard way. The soak test deliberately fires 6K-token prompts at the 4K deployment to prove they are rejected instantly and cleanly, twelve of twelve, before any DSP work. Defending the wall at the front door is part of a sound deployment, not an afterthought.

Failure class 3: lifecycle hygiene, or how to brick inference until reboot

The third class is not about memory size. It is about cleanup, and it is the one that produces the reboot-requiring hang.

Per request: reset, do not recreate. Between requests you must clear the dialog's state. There are two ways, and only one is safe. Recreating the whole context each time leaks the DSP's I/O virtual address space; do it enough and inference bricks until reboot. The correct move is to reset the existing dialog in place. In the serving shim I ran before moving to the vendor runtime, it was one line, deliberately chosen:

rc = lib.GenieDialog_query(dialog, prompt, SENTENCE_COMPLETE, cb, None)
reset_rc = lib.GenieDialog_reset(dialog)   # reset, NOT recreate

One long-lived dialog, reset between turns. Never a fresh context per request.

On shutdown: free, in order. Here is the one that caused the console flood. If you kill the process while it holds live FastRPC shared-buffer mappings, you orphan secure-world buffer registrations that now have no owner. The kernel then tries to re-register them, fails, retries, fails, forever: a measured flood on the order of 100,000 console lines, until you reboot. The cleanup obligation was important enough to write into the shim's own docstring:

def close(self):
    """Free NPU resources in order. Killing the process with live fastrpc
    shared-buffer mappings orphans QTEE shm-bridges (kernel then retries
    registration forever; console spam until reboot), so this MUST run
    on shutdown."""
    lib.GenieDialog_free(dialog)
    lib.GenieDialogConfig_free(cfg_handle)

The rule: install a signal handler, free the dialog and the configuration on SIGTERM, and never kill a live NPU process with kill -9 if you can avoid it. The DSP holds resources that normal process teardown does not know about; you have to hand them back explicitly.

The per-token tax

One last thing FastRPC explains, and it is the result on this board I found most counterintuitive. FastRPC is a round trip: marshal, call, wait, copy back. A token's worth of decode work is not one round trip but many, and they add up to tens of milliseconds of boundary overhead per token before any actual math. For prefill that is negligible, amortized across a batch of prompt tokens. Decode generates one token at a time, so every token pays the tax in full, and on a small model, where the matrix math per token is tiny, the tax is a large share of the time. That is why the CPU, which has no boundary to cross, holds its own on decode while losing prefill by five to seven times. The same-binary post has the measurement; the memory-hierarchy post has the other half of the reason, the shared bandwidth.

A checklist: verifying the FastRPC path on a new board

When you bring up NPU inference on a fresh board and want to know the plumbing is sound:

  1. Stub present? find / -name libcdsprpc.so. It is your CPU-side client.
  2. Device nodes present? ls /dev/fastrpc-cdsp*. No node, no compute DSP.
  3. Library path set, and pointing at your Hexagon version? hexagon-v73/unsigned for this board. Wrong version means a silent CPU fallback.
  4. Skels actually there? List the directory the variable points at; you should see the HTP and QNN skels.
  5. Prove offload, do not assume it. Run a CPU-versus-NPU A/B with the same binary. If the numbers do not move, the skel is not loading; go back to step 3.
  6. Budget the KV cache before choosing a context length. About 72 KB per token for a 4B model with 8-bit KV; keep the buffer well under the ceiling.
  7. Reject oversize prompts at the server. Defend the wall at the front door.
  8. Free on shutdown. Signal handler, then free the dialog and the configuration. Never orphan the buffer registrations.

Run that list and FastRPC stops being the invisible thing that breaks and becomes a boundary you can reason about.

Transferable principles

  • Everything crosses FastRPC. The boundary, stub, skel, and DMA-heap buffers, is the substrate every NPU workload lives on. Learn its parts; they are where the failures are.
  • The library path variable governs the compute DSP despite its name, and its failure is silent. A wrong or unset path reverts everything to the CPU with no error. First thing to check when offload "did nothing."
  • Context length is a hardware memory budget, not a configuration knob. The KV cache competes for a mapping ceiling of about 1 to 1.5 GB per context; over budget does not slow down, it fails to load. Do the KV arithmetic up front.
  • The DSP holds resources your process teardown does not know about. Reset dialogs, do not recreate them; free explicitly on shutdown. Install the signal handler.
  • The round-trip tax is why small models decode about as fast on the CPU. Boundary cost, not compute, is the bottleneck at decode; the accelerator's win is prefill and performance per watt.
  • The same physics should apply to other accelerators behind a call boundary with their own address space, not just Hexagon. Budget for the boundary, not just the FLOPs.
