On-device LLMs: the context window is the spec to watch

Notes from running Qwen3-4B on a Qualcomm NPU. August 2026.

I've been running Qwen3-4B on the NPU of a Qualcomm QCS9075 board. On this platform you don't so much load a model as install one: models ship as precompiled NPU binaries, and their shape — including the context window — is baked in when the bundle is compiled. The published bundle gives you 4K tokens.

4K sounded fine. Then I built an agent on top of it.

Here's the budget I was actually working with:

  • The system prompt ate about 700 tokens.
  • Every tool definition — the JSON schema the model needs to call an API — cost roughly 600 more.
  • With four tools loaded, that left under 1,000 tokens for the conversation, the tool's output, and the answer.

That last line is the whole problem. My agent has 12 tools, so I could only expose 4 at a time and had to rotate subsets. One fat tool result — a diagnostics dump, an interface table — could blow the window and fail the entire request. And chat history? Forget it. Every request was effectively single-shot.

Why the window is baked in

It's worth pausing on why this number is fixed at all, because it's nothing like the GPU world, where context length is a flag you pass at load time. On this stack, the NPU executes only precompiled static graphs. The model is exported as a pair of graphs sharing one copy of the weights — a prompt processor that consumes a fixed number of tokens per pass, and a token generator that produces one token per pass — and the KV cache isn't an internal buffer the runtime can grow. It's graph input and output, with a shape fixed at compile time. The window isn't a setting stored next to the model; it's the geometry of the compiled artifact. Changing it means compiling a different artifact.

(I went deep on this pipeline — the per-model adaptation, quantization, and what actually lives inside a compiled context binary — in a separate write-up.)

The recompile

My first instinct was to blame the model size. That instinct was wrong. Context length is just a compile-time parameter, and the vendor happens to publish exactly one configuration — but the compile pipeline, Qualcomm AI Hub, is open. So I recompiled the same model at 8K.

Mechanically, that means running the model's export through AI Hub with a different context-length setting: the pipeline re-exports the graphs at the new shape and compiles them in the cloud for the exact target chip. It's self-service for the models in Qualcomm's catalog — no vendor involvement, though not fast: the compile is an hours-scale, big-host-RAM affair, not an edit-and-reload loop. You do it once per operating point you want to own.

What 8K bought

What that bought me, on the same silicon:

  • The full 12-tool set fits. My test went from failing all six runs to completing every one.
  • Real tool outputs fit, without me aggressively truncating them.
  • Actual multi-turn conversation. Follow-up questions work now.
  • And the part I didn't expect to value most: independence. Once you can compile your own bundle, the vendor's published config is a default, not a ceiling.

What it cost

Now the bill — and I measured this rather than assuming, which turned out to matter. These compiled NPU graphs are fixed-shape, so every decode step pays for the whole window whether you use it or not:

  • The 8K build runs about twice as slow per turn on identical prompts — 1.9× at the median, 6.7 s to 12.9 s.
  • Accuracy stayed within a couple of points. Same weights; small numeric shifts flip the occasional borderline token.
  • The KV cache roughly doubled, ~350 MB to ~700 MB, which still has to clear the accelerator's per-context memory limit.

The slowdown isn't an inefficiency someone will optimize away — it's the same geometry that makes the window fixed. Because the decode graph has a static shape, each step attends over the full window regardless of how much of it is occupied, and the doubled KV cache is that much more memory traffic on a bandwidth-bound workload. You buy capacity with per-token time, every token.

For the record, the setup behind those numbers: six trials per configuration on identical prompts, on device. Under 4K, all six failed, dominated by context overflow on large tool results; under 8K, all six completed with the full toolset resident. Two honest caveats: the ~600-token schema figure comes from the one 4-schema configuration I had deployed, and I never benchmarked the alternatives — schema compression, routing between tool subsets, aggressive output truncation. The recompile made them unnecessary for my case, but for someone who can't recompile, they're the remaining levers.

Two operating points

So the 8K build doesn't replace the 4K one — it's a second operating point. Both bundles sit on the accelerator side by side: small window for snappy interactive turns, big window when the agent needs its whole toolbox. On compiled NPU stacks, you buy context with per-token time. The trick is owning the compile pipeline, so that trade-off is yours to make instead of the vendor's.

If you're evaluating small models for on-device work: look at the context window before the parameter count. It's the spec that separates a demo from a product.
