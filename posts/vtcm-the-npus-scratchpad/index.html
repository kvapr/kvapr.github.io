VTCM, the NPU's scratchpad

8 MB of on-chip SRAM that the compiler plans by hand. It is a large part of why compiled NPU models are fast, and it decides whether two models can share the chip.

This post explains one part of the Hexagon NPU that no spec sheet lists and no public document explains well: VTCM, the small software-managed memory that the vector and matrix engines are fed from. It covers what VTCM is, why it is not a cache, what contention for it looks like, how it differs from the NPU's other memory wall, and where this level of detail can be found in public. The measured size and the profiling observations are from a Qualcomm QCS9075 on the Dragonwing IQ-9075 EVK, Hexagon v73. A longer article on the NPU's whole memory hierarchy is planned; this is its first section.

What VTCM is

Running an LLM on a phone-class NPU means the model is compiled ahead of time into a fixed graph for the accelerator. On Qualcomm's Hexagon NPU, one small number ends up deciding a lot: the size of an on-chip memory called VTCM. On a QCS9075 board it is 8 MB. The chip reports it directly: threads 4, HVX 4, HMX 1, VTCM 8 MB.

VTCM (Vector Tightly Coupled Memory) is a block of SRAM inside the NPU, next to the vector and matrix engines. Those engines are so fast that board DRAM cannot feed them; data has to already be on-chip when an instruction wants it. VTCM is the staging area. DMA engines stream tiles of weights and activations from DRAM into VTCM, the engines process them at full speed, results stream back out. 8 MB holds the working tiles of a layer computation, not a model. Even a small LLM's weights are hundreds of times larger, so everything streams through this window.

Not a cache

The design property that matters: VTCM is not a cache. A cache manages itself invisibly. VTCM is a scratchpad managed by software: when a model is compiled for the NPU, the compiler plans exactly which tiles occupy which part of it at each step. That planning is a big part of why compiled models are fast. It also means every compiled model arrives with a claim on a specific slice of those 8 MB.

Contention

Contention is what happens when resident models' claims exceed the space, and it shows up two ways. If the claims plainly do not fit, loading can fail outright. On this board it did: a fourth graph context refused to place while two serving stacks held copies of the same large model, for what looks like this reason. The runtime reports it only as a packing failure, and the NPU's per-domain DMA address space is the other candidate. If the claims fit only by taking turns, the NPU time-shares VTCM between workloads, and each handover costs DMA traffic before any useful compute resumes. That is what profiling showed on this board when a vision model and an LLM ran together: the NPU's compute was not saturated, and the contention was VTCM time-sharing. True partitioning, each model holding its own slice at the same time, is only supported from Hexagon v81; this board's v73 can only take turns. The symptom to expect is not an error but latency jitter: the LLM's per-token time stutters whenever the other model takes its turn.

Two different walls

Worth separating from a different limit this board also has: the roughly one-gigabyte DMA mapping space, which is about how much board DRAM the NPU can have mapped at once in a compute domain. That is the wall the 8K-context KV cache in the context-window post had to clear. It is address space for the big slow memory; VTCM is the tiny fast memory. Two different walls, and two resident models can hit either, which is why the load failure above is attributed to VTCM only as the likelier cause.

Two compute DSPs

The QCS9075 has two compute DSPs, each with its own 8 MB pool. Pinning an LLM to one domain and a vision model to the other should remove most of the contention. "Should" is doing real work in that sentence: no published measurement seems to exist for an LLM agent and a vision pipeline sharing one edge NPU, which makes it worth measuring properly.

For on-device AI, DRAM size gets the spec-sheet attention. Whether a model runs fast, and whether two can coexist, is decided megabytes at a time, on-chip.

Where to read more

Public sources for this level of detail, best first. Links checked on 3 September 2026.

  • llama.cpp, the Hexagon backend. Open code that programs this NPU, and where the hardware-report line above comes from. Search the repository for "hexagon" or "VTCM". The most concrete public documentation that exists, better than any prose for seeing how VTCM is actually allocated and used.
  • Hexagon SDK. HVX programming and the compute-resource APIs through which software requests VTCM. The documents ship inside the SDK download rather than on the web. This is the public boundary made visible: HVX is fully documented there, HMX is not.
  • AI Engine Direct (QNN, QAIRT) documentation. The runtime level above: the HTP backend, performance modes, how graphs declare VTCM needs, and the device architecture versions. This chip is v73. Deep links on that site move; re-find it by searching for "AI Engine Direct SDK".
  • Hot Chips archives. Qualcomm's Hexagon NPU and Cloud AI 100 talks. The slides give the architecture rationale, why a software-managed scratchpad and how DMA overlaps compute, that the SDKs never explain.
  • AI Hub and ai-hub-models. The compile pipeline and the per-model recipe structure; what "supported architecture" concretely means for this NPU.
  • GenieX documentation. The serving stack that runs compiled bundles and GGUFs on this board.
  • arXiv. No single stable link. Search "on-device LLM inference NPU" and the mllm-NPU line of work, which describes HTP internals from a practitioner's measurement perspective.
