The serving path is the model

Same weights, same benchmark, same 4-bit quantization class: 0% through one serving stack, 100% through another, and it happened four times, with four different failure signatures.

This post is about one measurement that changed how I evaluate small models for tool calling. Over the summer I ran several open-weight models through different serving stacks on a Qualcomm NPU and on a CPU, against the same 65-case benchmark. The same model scored 0% through one stack and 100% through another, and it happened four times, each with a different cause. The post walks through the four cases, shows that the tool-schema design most people blame first made no measurable difference, and ends with the checks I now run before blaming a model. Board: Qualcomm QCS9075 on the Dragonwing IQ-9075 EVK; models quantized to 4 bits; measurements from July and August 2026.

Both rows are measured, August 2026, on the same 65-case tool-calling suite with strict end-to-end grading — the 100% includes exact-key, type-faithful nested arguments. The model is identical. The quantization is the same 4-bit class. The prompts are identical. What changed is the serving path: how the request became tokens, and how the generated text became a structured tool call. (Strictly, the compute unit and the exact 4-bit scheme also differ between the rows — but the runtime maintainer later confirmed two serving bugs as the cause, which is why the attribution to the serving path is documented rather than inferred; the full story is in rung 1.)

If a model can score 0 and 100 on the same benchmark depending on how you serve it, then a tool-calling benchmark score is not a property of a model. It is a property of a (model, serving path) pair. This article is the evidence for that claim: a four-rung ladder of models I measured through at least two serving paths each, the failure signature at each rung, one null result about the thing people expect to matter (schema design — it didn't), and the methodology I now follow before blaming any model for anything.

Context for new readers: I run an intent-driven network-management agent fully offline on a Qualcomm QCS9075 (Dragonwing IQ-9075 EVK — evaluation kit). The language model runs on the board's Hexagon NPU (neural processing unit) as a compiled 4-bit bundle. Earlier articles cover the porting and benchmarking story; this one stands alone.

What the serving path is

The serving path is everything between an OpenAI-style API request and the structured tool_calls array the agent consumes. It has exactly two transformations, and each one is a place where a perfectly good model can be made to look broken:

  1. Template in. The serving layer renders your messages and tools into the literal token sequence the model was trained to see — the chat template. Every model family has its own: its own special tokens, its own place and format for tool schemas, its own way of marking a tool-call turn.
  2. Parser out. The model emits text. The serving layer must recognize the tool-call portion and convert it into structured JSON the client can act on. If the parser expects a wrapper tag the model didn't emit — or the detokenizer corrupted — the call is silently dropped.

Failure point 1 degrades what the model produces (it never saw the tools, or saw them in a foreign format). Failure point 2 discards what the model produced (correct payload, unrecognized wrapper). The two look identical from the outside — the benchmark just reads 0 — which is exactly why you have to read raw outputs to tell them apart. More on that below.

Two serving paths recur in this article. Path A is llama.cpp running the GGUF (llama.cpp's model file format) on the board's CPU with --jinja, which applies the model's own native chat template — my reference path. Path B is the compiled route: W4A16 (4-bit weights, 16-bit activations) context binaries running on the NPU, served either by my own shim or by GenieX, Qualcomm's umbrella runtime (developer preview as of August 2026) with two backends, qairt for compiled bundles and llama_cpp for GGUFs.

The benchmark, briefly

All numbers come from the same harness: 65 tool-calling cases in four difficulty levels (status queries, enable/disable actions, single-parameter changes, multi-parameter changes) against a managed PoE (Power over Ethernet) switch's tool schemas. Grading is tiered — right tool, right command, right parameters (lenient and strict), right device — and "e2e" (end to end) means all of them at once. Temperature 0. The suite is stable: three fully shuffled orderings of the production configuration scored an identical 96.9% (measured), and run-to-run flips across otherwise-healthy configurations are one or two cases (~2–3 points). So the swings below are not noise: the observed serving-path swings are 36 to 100 points, an order of magnitude above the flip behavior.

Rung 1: Gemma-4-E4B — 0% and 100%, both failure points at once

This is the war story.

Symptom. Mid-August 2026, a compiled W4A16 Gemma-4-E4B bundle for the QCS9075 appeared in Qualcomm's AI Hub catalog (geniex_qairt runtime only). This mattered because Gemma-4-E4B had already scored 100% on my suite via llama.cpp on a CPU — the first model to do so. After working through an unrelated registration bug (a truncated download that the cache accepted as complete — its own story, told elsewhere), the bundle served stably on the NPU. The bench run: 0% e2e, 0% tool selection. Zero for 65. Median latency 3.2 s, so the model was generating fluently. It just never made a tool call the runtime recognized.

Hypotheses. Either the model can't tool-call at this quantization (weights), the tools never reach it (failure point 1), or its calls are emitted but dropped (failure point 2).

Instrument. The bench harness stores every raw completion. Reading them settles it in minutes. Three real outputs from the 0% run (measured):

<|tool_call>call: "show_all_ports_status"
{"tool_call": "show_port_status", "port_id": "5"}
{"tool_call": "show_system_info"}

Evidence. Two observations. First, the model is trying to call tools — but it invents tool names. show_all_ports_status is a command name in my nested schema, not a tool; the correct call is query_device_info with command_name: "show_all_ports_status". A model that scored 100% on this exact nested schema through llama.cpp does not suddenly forget the schema exists — unless it never saw it. That is failure point 1. Second, even the malformed attempts ({"tool_call": ...}, <|tool_call>-prefixed lines) are never converted into structured tool_calls — that is failure point 2. On some cases it produced prose asking for confirmation instead, which is what a tool-trained model does when it knows tools exist in principle but has no schemas in front of it.

Fix. I reported both to the GenieX maintainer with the 0-vs-100 evidence. The maintainer confirmed two distinct bugs (documented): the tool definitions were being dropped before reaching the qairt Gemma-4 chat template, and Gemma-4's tool-call output format wasn't parsed into structured tool_calls. Both failure points, independently broken, for one model, in one runtime version. Fixes are in a pull request; an alpha build (v0.4.1-alpha.2) is published for retest. My Gemma-4 NPU retest is in progress — treat all Gemma-4-on-NPU numbers as pending as of August 2026.

Lesson. A model scored 0% for 65 consecutive cases and the model was not the problem either time. If I had benched Gemma-4 only through the compiled path — the natural thing to do, since the NPU is the deployment target — I would have concluded "Gemma-4 can't tool-call at 4-bit" and moved on. That conclusion would have been wrong by 100 points.

One latency footnote for honesty: the 100% llama.cpp run's 2.4 s median was measured on a 20-core dev host, not board silicon. It's a capability number, not a deployment latency.

Rung 2: base Qwen3-4B — correcting my own July conclusion

This rung is a public correction, which the ladder demands I make.

In July I tested the base (non-instruct, April-2025) Qwen3-4B as a compiled NPU bundle under GenieX v0.3.17-alpha, hoping its cleaner token handling would let me drop a client-side adapter. It scored 10.8% e2e served natively. The model omitted the <tool_call> wrapper tag about 60% of the time, emitting bare JSON that GenieX's tag-requiring parser silently dropped (failure point 2). Re-scoring the captured outputs with a tag-agnostic parser recovered those — 24.6%. Still far below production. The failure signature in the remaining misses: the model flattened command names into tool names, calling show_poe_status or configure_trunk_allowed_vlans as if they were top-level tools and often omitting command_name entirely.

My July conclusion, written in the experiment log: base Qwen3-4B has structurally weak nested-schema adherence; the 2507-Instruct update fixed exactly this; the experiment re-validates the production model choice. It was a tidy conclusion. It fit the data. It even had a mechanism.

In August I ran the same base model through llama.cpp on the board's CPU with its native chat template, same 65 cases, same nested schema: 100% (65/65, strict parameters included — measured).

So the July conclusion was chiefly a serving artifact. The "structural" nested-schema weakness disappears when the model is served through the template it was trained on. What I had actually measured in July was: base Qwen3-4B degrades badly when the prompt format deviates from its training template, and the compiled-path serving of that era deviated. That is a real and useful finding — instruct-tuned models tolerate template drift better than base models (inferred from this pair plus rung 3) — but it is a different finding from "this model can't follow nested schemas."

The July decision itself survives: 24.6% through the deployment path is disqualifying regardless of the cause, and the production model still wins. But the reasoning was wrong, and reasoning is what transfers to the next decision. A 75-point serving swing was hiding inside a conclusion about model quality.

Rung 3: Llama-3.1-8B — 55% vs 90.8%, the partial version

Not every rung is 0-or-100. In July, Llama-3.1-8B scored 90.8% e2e through llama.cpp's native template (measured, full 65 cases) and 55% through my then-current shim's NPU path (measured, n=20, Level-1 cases only — a screening run, so treat the number as coarse). The signature is the diagnostic part: tool selection stayed at 90% while e2e fell to 55%. The model was picking the right tool and then failing on format — the reading I take from that signature (inferred, not instrumented at the time) is that my shim's hand-rolled Llama templating mangled the native tool-call format enough to corrupt arguments, not enough to destroy intent.

This is what a partially wrong serving path looks like: not a cliff, a 36-point tax, concentrated in the strictest grading tiers. It is also the most dangerous kind, because 55% looks like "mediocre model" rather than "broken plumbing," and nothing about the score invites you to check the plumbing.

Rung 4: same model, same bundle, different runtime version

The cleanest control in the ladder: production Qwen3-4B-Instruct-2507, one compiled W4A16 bundle, byte-identical weights, across GenieX versions.

Under v0.3.17-alpha, structured tool calls never populated (probe-level observation, not a full bench). The cause is documented in earlier articles: the quantized model's <tool_call> special token gets corrupted by the detokenizer into garbage text — Qualcomm inspected the logits and confirmed it is quantization-induced — and the version's parser required the literal tag it would never see. Correct JSON payload, discarded wrapper: failure point 2 in its purest form.

Under v0.3.19, whose parser scans for balanced JSON instead of trusting the tag (a fix merged as GenieX PR #1298, an approach my bug reports proposed — documented): 93.8% e2e / 96.9% tool selection / 7.25 s median on the same bundle (measured). The model didn't change. The weights didn't change. The parser learned to tolerate a mangled wrapper, and the score went from nothing to production-grade.

So the full dynamic range: a broken serving path costs 36 to 100 points; the residual differences between correct serving paths cost about 5. The serving path is not a rounding error on model choice. On this evidence it is the larger variable.

The counterpoint: schema shape measured as a non-factor

When tool-calling accuracy disappoints, the first thing most people redesign is the tool schema. My schema is an obvious suspect: it nests commands inside wrapper tools (4 tools, each with a command_name parameter) instead of exposing each command as its own tool. Rung 2's July reading — "base models can't handle nesting" — pointed the same way. So I tested it directly: the nested 4-tool schema versus a flattened variant where each command is its own top-level tool (25 tools), both served through the identical llama.cpp CPU path so that serving is held constant (measured, August 2026):

ModelNested (4 tools)Flat (25 tools)
Qwen3-4B-250796.9%98.5%
Qwen3-4B (base)100%96.9%

No effect. The differences are one to two cases, in opposite directions for the two models — indistinguishable from the run-to-run flip behavior documented above. The variable everyone reaches for first moved the needle roughly 2 points in no consistent direction; the variable almost nobody varies moved it up to 100. I keep this table next to the ladder because the contrast is the finding: intuition ranks schema design far above serving plumbing, and measurement ranks them the other way around by more than an order of magnitude.

(Scope note, inferred: this null result is two models on one suite with well-matched templates. Schema design plausibly matters more at larger tool counts, longer schemas, or through a serving path that renders schemas poorly — which would, again, be the serving path talking.)

The methodology this forces

Two rules, both cheap, both of which I now follow without exception.

Rule 1: bench every model through at least two serving paths before judging it. One of them should be the model's reference path — llama.cpp with --jinja, or the vendor's own reference server — because that is the closest you can get to the template the model was trained on. If the two paths agree, you've learned about the model. If they disagree, you've learned about a serving path, and the higher score is the better estimate of model capability.

Rule 2: read raw outputs before blaming the model. Every failure signature in this article was legible in the raw text within minutes: invented tool names (tools never reached the model), missing wrapper tags (parser dropped valid payloads), correct tool with mangled arguments (template drift). A benchmark score compresses all of these into one indistinguishable number.

The order matters because the cheap checks come first and the expensive conclusion — "the model is bad" — comes last. In four out of four rungs on this project, the expensive conclusion was the wrong one. And the evidence you gather on the way is exactly what a runtime maintainer needs: my 0-vs-100 tables, with raw outputs attached, turned into confirmed bugs and merged fixes rather than a shrug.

There's a third practice implied by rung 4: re-run the bench after every runtime upgrade, even when the model is untouched. A serving stack in developer preview changes monthly (as of August 2026, GenieX has moved through v0.3.17-alpha, v0.3.19, v0.4.0, and v0.4.1-alpha.2 in my logs), and each version is, in effect, a different serving path.

What this means for eval leaderboards

Every public tool-calling leaderboard number is a (model, serving path) measurement wearing a (model) label. For cloud models this is mostly harmless — the vendor controls the one serving path everyone uses, and it's the same one you'll deploy against. For open-weight models it is not harmless at all: the score depends on which runtime the eval harness used, which template that runtime shipped for that model that month, and how tolerant its parser is. Rung 1 is the existence proof: there is a runtime through which Gemma-4-E4B "scores" 0%, and a same-week runtime through which it scores 100%, and nothing on a leaderboard distinguishes them.

The practical reading, inferred but I'd defend it: for open-weight models, treat any tool-calling score whose serving stack isn't specified — runtime, version, template source, parser behavior — as unverifiable. And treat low scores with more suspicion than high ones. A high score proves the model and the path both work. A low score proves only their conjunction fails, and this article is four demonstrations that the path is the more likely culprit. On-device deployments compound this: quantization can corrupt the very special tokens the parser keys on (documented — Qualcomm confirmed the mechanism is quantization-induced, with no current fix), so the parser's tolerance becomes part of the model's effective accuracy.

The through-line of this series holds here too. An NPU doesn't run "a model" — it runs operations, fed by a template and read back through a parser. Everything in this article follows from taking the second half of that sentence as seriously as the first.

Transferable principles

  • A tool-calling benchmark score is a property of a (model, serving path) pair. Never attribute it to the model until two paths agree.
  • Bench through the model's reference template (llama.cpp --jinja or equivalent) before any custom or vendor path. The best score across paths is your capability estimate; the deployment path's score is your product number.
  • Read raw completions before concluding anything. Invented tool names mean the tools never arrived; intact JSON with a wrong wrapper means the parser dropped it; right tool with wrong arguments means template drift.
  • Partial serving damage (rung 3's 36-point tax) is more dangerous than total damage, because it impersonates a mediocre model instead of announcing a broken path.
  • Write parsers tag-agnostic: scan for balanced JSON, don't trust wrapper tokens. Quantization can corrupt exactly the special tokens you'd anchor on.
  • Re-bench after every runtime upgrade. A new runtime version is a new serving path.
  • Schema shape (nested vs flat) measured as a non-factor here — spend redesign effort on the serving path first, schema aesthetics later.
  • Base models tolerated template drift worse than instruct-tuned ones in the pairs measured here (inferred from two model pairs, not a general law); a base model's bad score through a nonstandard path says almost nothing about its ceiling.
